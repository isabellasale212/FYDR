# Demo data for Friday 18 September — twelve weeks of Glenbrae

**The script:** `scripts/seed-demo-history.mjs`. Built and tested on scratch on
15 September (written six times; a re-run is a clean replacement). **Isabella
runs it against production herself, once**; the builder never touches production.
The club is renamed in the same pass — seed.sql's Ashcombe Rugby Club becomes
**Glenbrae Rugby Club**, with Super Series opposition (Ayr, Stirling Wolves,
Heriot's, Watsonians, Boroughmuir Bears, Currie Chieftains); the accounts'
`@ashcomberfc.example` addresses are auth-level and stay.

## How to run it

```
# dry run — reads, prints what it would remove and write, changes nothing
node --env-file=.env.production.explicit scripts/seed-demo-history.mjs --target production

# the real thing, once, on Wednesday or Thursday (not Friday morning)
node --env-file=.env.production.explicit scripts/seed-demo-history.mjs --target production --write
```

It prints the host it is pointed at (never the credentials), refuses if the
connection string's project ref is not the one `--target` names, and refuses
if organisation `a0000000-…0001` is not the demo club (Ashcombe or Glenbrae).
Everything is one transaction: a failure rolls back and prints why. It takes
about two minutes. The audit triggers it stands down for the run are stood back
up inside the same transaction before the commit (ALTER TABLE is transactional,
so a failure or a dropped connection rolls the disable back with everything
else), and the catalogue is checked after the commit — and after any rollback —
for a trigger left disabled; it exits non-zero and says so if one is.
The window is anchored on the day it runs — "this week" is the week it runs
in, so run it on the day you want the demo's "today" to be near.

## What it removes first

The organisation's existing history in every table it writes — all synthetic,
per the 15 September runbook: sessions and everything hanging off them
(participants, attendance, ratings, GPS, gym logs, test results, compliance
expectations), fixtures and match sheets, wellness entries, weigh-ins,
nutrition check-ins, availability, flags and their actions, programme
assignments, team allocations, the Rehab group's memberships, and — since 16
September — every `athlete_devices` row for the organisation (real or
synthetic; a phone that opens the app again writes its own row back, the
beacon upserts). Injuries are
**retired** (`deleted_at`), not removed — a subject-access clinical review may
reference one. Kept untouched: the organisation, users and roles, athletes,
groups, teams, the season, thresholds, week templates, programmes and
exercises, test definitions, nutrition targets, meal library, leaderboards,
notification preferences, the audit log. Reference data it needs and does not
find (a gym programme with four blocks, a rehab programme, the seven test
definitions, a club nutrition default) it creates by name.

## What is deliberately incomplete

- Wellness check-ins at 75% of athlete-days across the squad; three athletes
  (Harry Ainsley, George Palmer, Seb Ellery) check in on roughly a third of
  days; one athlete's check-ins fall away in the last fortnight (below).
- 91% of attended sessions are rated; 26 ratings are a genuine 0 (a pool
  recovery rated as rest); a session an athlete did not attend has no rating.
- Ollie Delaney rates about half his sessions — 15 of the last 28 days — so
  his ACWR is **withheld** ("needs 21 of 28"), not estimated. Adam Selby, back
  from injury, is withheld the same way (6 days). Nine athletes in all.
- One in ten weigh-ins missed; GPS units not charged in weeks 2 and 6 (no unit
  skills record those weeks); about a quarter of gym sessions unlogged; six in
  ten weekly nutrition check-ins answered.
- Missing is an absent row everywhere; nothing is written as zero.
